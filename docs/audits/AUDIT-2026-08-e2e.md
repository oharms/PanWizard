### Themes

1. **Runtime-parity breakage is the dominant High-severity theme (H1, H4, H6).** The installer's path-rewrite step only recognizes the `~/.claude/` (and, for hooks, `./.claude/`) prefix. Shipped content authored with any other prefix — `./.claude/` in pan-verifier/pan-plan-checker, bare `.claude/` in learn.md/optimize.md — ships verbatim and breaks on the four non-Claude runtimes and on global installs. The Codex hooks ESM crash (H1) is the same class: one runtime excluded from a protection every other runtime gets. A single hardening pass on the installer's rewrite/marker logic plus a content-lint rule (only `~/.claude/` allowed in shipped content) closes the whole class.

2. **Dead gates.** The anti-rubber-stamp `verify reconcile` exit code (H3) is dead code because `output()` unconditionally exits 0 first — the auto-advance gate in exec-phase can never stop a rubber-stamped verification, and CHANGELOG's claim to the contrary is false. The installer's model-capability warning is similarly unreachable (M-class, `finishInstall` references an undefined variable inside a swallowed try/catch). Both were missed because tests cover the pure functions but never the CLI exit path.

3. **Docs that actively mislead survived audit pass 1 (H5, H7–H9).** README's development-install instructions cannot succeed (the installer hard-refuses its own repo root); Codex troubleshooting points at a directory the installer deletes; EXAMPLES.md promises phase renumbering that the workflow explicitly never does; and model-profiles.md still documents the pre-COST-RESET profile table, silently demoting agents to cheaper models when orchestrators follow it.

4. **One real data-loss bug in core (H2).** `bus drain --mode consume` truncates the whole channel file after a limited read — unread messages beyond `--limit`/`--offset` (or beyond the 1000-message default on large channels) are destroyed.

5. **The Medium tail (80) is mostly drift and edge-case robustness**, concentrated in shipped content (stale cross-references, renamed-command leftovers, contradictory instructions) and core-module edge paths (crashes on malformed input, wrong exit codes, silent no-ops). The Low tail (48) is hygiene: embedded counts that violate the counts policy, minor link rot, cosmetic drift.

6. **Test coverage is broad but has named holes**: pan-context-monitor.js (134 lines of threshold/debounce logic) has zero behavioral tests, pan-check-update.js's logic lives in an untestable inline `node -e` string, and global-install mode has no positive coverage on any runtime.

### Highest-leverage fixes

1. **Installer parity pass** — write the `{"type":"commonjs"}` marker for Codex (H1), extend path rewriting or fix the offending sources (H4, H6), and add a shipped-content lint asserting the canonical `~/.claude/` prefix. Fixes 3 of 9 Highs and prevents recurrence.
2. **Give `output()` an exit-code path** and add CLI-level exit-code tests for `verify reconcile` (H3) — this un-deadens the auto-advance gate and the same pattern likely applies to other gates routed through `output()`.
3. **Fix `bus drain` consume-mode truncation** (H2) — small, contained, real data loss.
4. **Docs correction batch** (H5, H7–H9 plus the Medium/Low doc tail) — mechanical once enumerated; every item below carries a concrete fix.

### Installer & runtimes

#### H1. Codex local install ships CommonJS hooks but deliberately skips the {"type":"commonjs"} package.json marker — all 4 Codex hooks crash in ESM projects

`bin/install.js:2101` · Installer & runtimes

**Failure scenario:** User project has "type": "module" in its root package.json (any modern ESM project). Run `node bin/install.js --codex --local`. The installer copies CommonJS hooks (pan-check-update.js etc., all using require()) into .codex/hooks/ and registers them in .codex/hooks.json, but the marker write is guarded by `if (!isCodex)`, so .codex/ gets no package.json. Node resolves module type by walking up from .codex/hooks/pan-check-update.js to the project's ESM package.json. Reproduced live: spawning the installed hook in a {"type":"module"} project exits 1 with `ReferenceError: require is not defined in ES module scope`. Every registered hook (SessionStart, PostToolUse, SubagentStop x2) fails on every trigger — update check, context monitor, cost logger, and trace logger are all dead for Codex local installs in ESM projects. The other four runtimes get the marker precisely to prevent this (the installer's own comment: "Prevents 'require is not defined' errors when project has 'type': 'module'").

**Evidence:**

```
install.js:2101-2113: `if (!isCodex) { // Write package.json to force CommonJS mode for PAN scripts // Prevents "require is not defined" errors when project has "type": "module" ... fs.writeFileSync(pkgJsonDest, '{"type":"commonjs"}\n');` — while 2115 `if (!isOpencode)` installs hooks for Codex and 2271-2277 registers them: `const hooksJsonPath = path.join(targetDir, 'hooks.json'); ... lib.mergeCodexHooksConfig(...)`. Live repro output: `exit: 1 / const fs = require('fs'); ^ [ReferenceError]`.
```

**Suggested fix:** Drop the `!isCodex` exclusion (write {"type":"commonjs"} into .codex/ too), or rename the shipped hooks to .cjs for the Codex target and register the .cjs paths in hooks.json.

### Core modules

#### H2. bus drain --mode consume permanently destroys unread messages beyond the read limit

`pan-wizard-core/bin/lib/bus.cjs:161` · Core modules

**Failure scenario:** Publish 5 messages to a channel, then run `pan-tools bus drain ch --mode consume --limit 2` (both flags documented in CLI-REFERENCE.md §bus drain). Verified live: drain returns 2 entries with more:true, then truncates the whole file — readChannel afterwards shows 0 remaining; the 3 unread messages are unrecoverable. Same loss occurs with no flags on any channel holding more than DEFAULT_DRAIN_LIMIT (1000) messages: the first consume silently deletes the tail. Also occurs with --offset (entries before offset are destroyed).

**Evidence:**

```
drain(): `if (mode === 'consume') { try { fs.writeFileSync(file, '', 'utf-8'); }` — unconditional truncation after `const read = readChannel(cwd, channel, opts);` which honors `limit`/`offset`. Empirical: drained entries: 2, total: 5, more: true → left in channel after consume: 0.
```

**Suggested fix:** In drain(), when mode==='consume' and read.more is true (or offset>0), rewrite the file with the un-drained lines instead of truncating to empty (read all lines, splice out the consumed window, write back the remainder). Alternatively refuse consume+limit/offset combinations.

#### H3. verify reconcile always exits 0 — the anti-rubber-stamp auto-advance gate never fires

`pan-wizard-core/bin/lib/verify.cjs:494` · Core modules

**Failure scenario:** A phase has verification.md with 'status: passed' but its plan's must_haves artifacts fail substance checks (e.g. a 2-line stub where min_lines: 30 is required). exec-phase.md's auto-advance gate runs 'pan-tools verify reconcile ${PHASE_NUMBER} --raw; RECONCILE_EXIT=$?' and stops only when RECONCILE_EXIT is non-zero. Because output() in core.cjs unconditionally calls process.exit(0) (core.cjs:193), the subsequent 'process.exit(r.reconciled ? 0 : 1)' is dead code and RECONCILE_EXIT is always 0. Empirically confirmed in a fixture: reconcile printed 'invalid' (contradiction detected) yet exited 0 in both --raw and JSON modes. Result: a rubber-stamped verification auto-advances to the next phase — the exact failure ADR-0036 says this gate closes. CHANGELOG.md:178 falsely states 'a claimed pass over failing checks exits non-zero'. Tests (tests/verify.test.cjs) only cover the pure reconcilePhase() function, never the CLI exit code, so this was never caught.

**Evidence:**

```
verify.cjs:493-494: `output(r, raw, r.reconciled ? 'valid' : 'invalid');\n  process.exit(r.reconciled ? 0 : 1);` — core.cjs output() ends with `process.exit(0);`. Fixture run: stdout 'invalid', RECONCILE_EXIT=0. exec-phase.md:679-681 gates solely on `RECONCILE_EXIT=$?`.
```

**Suggested fix:** In cmdVerifyReconcile, don't rely on code after output(): write the payload to stdout directly and call process.exit(r.reconciled ? 0 : 1), or add an exitCode parameter to output(). Add a CLI-level test asserting exit code 1 on contradiction.

## Medium findings

### Installer & runtimes

#### M1. Copilot agent converter extracts tools from `allowed_tools:` block-list frontmatter that zero PAN agents use — all 24 Copilot agents ship without tool restrictions

`bin/install-lib.cjs:539` · Installer & runtimes

**Failure scenario:** Every agent in agents/*.md declares tools inline as `tools: Read, Grep, Glob, Bash` (verified: all 24 files use this form; grep for `allowed_tools` in agents/ returns nothing). convertClaudeToCopilotAgent only matches `allowed_tools:` followed by a YAML block list, so copilotTools is always empty and the emitted .agent.md frontmatter contains only name+description. Verified live: installed .github/agents/pan-conductor.agent.md has no tools field. Consequence: read-only-by-design agents (e.g. pan-distiller: Read, Grep, Glob; pan-optimizer: Read, Glob, Grep) run on Copilot CLI with the default full toolset including write/bash — the claudeToCopilotTools mapping table and convertCopilotToolName are effectively dead code for agents. Contrast: the Gemini converter (install-lib.cjs:272) and OpenCode converter (336) both parse the inline `tools:` form.

**Suggested fix:** Parse the same frontmatter shapes as the Gemini/OpenCode converters (`tools:` inline comma list and `allowed-tools:` block list) in convertClaudeToCopilotAgent, mapping via convertCopilotToolName.

`bin/install.js:222` · Installer & runtimes

#### M3. cleanupOrphanedFiles uses unguarded fs.unlinkSync — a locked legacy file aborts the entire install with an unhandled exception

`bin/install.js:770` · Installer & runtimes

**Failure scenario:** Upgrading a pre-v1.9 install on Windows where hooks/statusline.js or hooks/pan-notify.sh exists and is locked (open editor, antivirus scan, or the statusline hook currently executing). cleanupOrphanedFiles is called directly at install.js:1804 outside any try/catch, and its `fs.unlinkSync(fullPath)` at 770 has no guard — EBUSY/EPERM throws, the installer dies with a raw stack trace before any copy stage, and neither the failures[] path nor INSTALL_WARNINGS reporting runs. Every other deletion in the installer is wrapped (`try { fs.unlinkSync(...) } catch (err) { pushInstallWarning(...) }` at 335, or bare catch elsewhere); this is the one remaining unguarded delete on the install path.

**Suggested fix:** Wrap the unlinkSync in try/catch and route failures through pushInstallWarning('staleCleanup', relPath, err).

#### M4. Upgrade path never sweeps stale Claude skill shims (skills/pan-*.md) — shims for removed/renamed commands persist forever and point at nonexistent commands

`bin/install.js:1937` · Installer & runtimes

The shim loop (1942-1951) only writes shims for current commands; unlike every other command surface (OpenCode flat commands delete pan-*.md first at 333-336, Codex/Copilot skills sweep pan-* dirs at 390-395/630-634, commands/pan is wiped wholesale by copyWithPathReplacement), skills/ is never cleaned. #### M5. Model-capability warning (E-9) is dead code: finishInstall references undefined `targetDir`, ReferenceError swallowed by bare catch — warning can never fire

`bin/install.js:2481` · Installer & runtimes

**Failure scenario:** User has `"model": "claude-3-haiku-20240307"` (or any model detectModelCapabilities flags as lacking 1M ctx / extended thinking) in .claude/settings.json and runs the installer. #### M6. Statusline overwrite guard only inspects the first statusline-capable runtime — existing custom statuslines in Gemini/Copilot are silently clobbered

`bin/install.js:2658` · Installer & runtimes

Every re-fire now produces a junk row with token_source:'transcript' and clamped:false, indistinguishable from a genuine zero-token run; /pan:cost counts it as a real agent spawn, inflating spawn counts and halving per-agent averages. Second concrete trigger: a project with BOTH a global and a local PAN install (both documented, README lines 154-155) registers two cost-logger commands (different paths, so Claude Code runs both); they share `.planning/metrics/.cost-cursor.json`, so the second process sees the advanced cursor and appends a zeros row on EVERY SubagentStop. pan-trace-logger.js has the identical defect (isDuplicateCompletion, lines 400-416, plus its own cursor).

**Suggested fix:** When the transcript slice is empty (lineCount === since) AND the previous ledger row has the same session/agent/transcript, skip the append entirely (a re-fire), or extend the duplicate check to treat an all-zero slice row following a real row for the same agent+session as a duplicate. ### Security & hygiene

#### M79. saveLocalPatches path-traversal guard only blocks forward-slash '..', bypassable by backslash on Windows

`bin/install.js:1687` · Security & hygiene

**Failure scenario:** saveLocalPatches iterates manifest.files keys and, for each relPath, reads path.join(configDir, relPath) and copies it to path.join(patchesDir, relPath). The traversal guard is `if (relPath.split('/').includes('..')) continue;` — it splits on '/' only. On Windows path.join treats backslash as a separator, so a manifest key like `..\..\..\secret` is a single element that does NOT include('..') and slips past the guard; path.join then resolves it outside configDir (verified: path.join('C:\\work\\clonedrepo\\.claude','..\\..\\..\\Users\\victim\\.ssh\\id_rsa') === 'C:\\Users\\victim\\.ssh\\id_rsa'). Threat model: a victim runs `pan install`/update inside a cloned untrusted repo that ships a poisoned `.claude/pan-file-manifest.json` with backslash-'..' keys; saveLocalPatches (called before files are overwritten) then reads a file outside the target dir and writes a copy to a backslash-'..' path that also escapes patchesDir. Impact is bounded (source and dest are yoked to the same relPath, so it is a one-hop file relocation of an already-readable file, not arbitrary-content write) which is why this is Low, but the guard is specifically meant to stop '..' escape and is incomplete for Windows separators.

**Suggested fix:** Normalise separators before the check, e.g. test `relPath.split(/[\\/]/).includes('..')` (or reject any key where path.relative(configDir, path.join(configDir, relPath)) starts with '..'). Apply the same normalisation to the equivalent guard used for the Codex ../.agents keys.
